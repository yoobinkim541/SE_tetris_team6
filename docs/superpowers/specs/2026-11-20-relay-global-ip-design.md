# 다른 LAN 간 P2P 대전: 서버 경유·global IP:바깥 포트 방 구분 (Challenge) 설계

- 브랜치: `challenge/relay-global-ip` (origin/develop `d432f1c`에서 분기). **develop·main에 병합하지 않는다** (요구사항 3 p12).
- 상태: 설계 초안, 사용자 승인 대기.

## 1. 의도

지금 P2P 대전은 같은 LAN에서만 된다. 서로 다른 집·학교·핫스팟에 있는 두 사람이 **공유기 설정(포트포워딩) 없이** 대전하게 한다.

요구사항 p8의 흐름("호스트는 주소를 화면에 보여 주고, 클라이언트는 주소를 입력해 접속")은 그대로 둔다. 보여 주고 입력하는 주소가 LAN 주소 대신 **global IP + 바깥 포트**가 될 뿐이다.

## 2. 목표 · 비목표 · 실패로 보는 것

- **목표**
  - 서로 다른 LAN의 두 PC가 Oracle 서버(`158.179.174.70`)를 거쳐 대전한다.
  - 호스트 화면에 `global IP`와 `바깥 포트`를 보여 주고, 친구는 기존 접속 화면의 IP 칸·포트 칸에 그대로 입력한다.
  - 연결된 뒤의 로비·경기·재대전·heartbeat·지연·끊김 처리는 기존 코드를 바꾸지 않고 그대로 동작한다.
  - 같은 global IP를 쓰는 여러 호스트(같은 실습실·와이파이·핫스팟)를 정확히 구분한다.
- **비목표:** 로비 코드(파킹), NAT 홀펀칭, 채팅·다인 대전, 사용자 인증·암호화, 서버가 게임 엔진을 돌리는 방식.
- **실패로 보는 것**
  - 기존 LAN 대전 동작이나 테스트가 바뀌는 경우.
  - 같은 global IP의 다른 팀 방에 잘못 붙는 경우.
  - 서버가 꺼졌을 때 게임이 멈추거나 오류 없이 대기만 하는 경우.

## 3. 방식 (선택: B안)

| 안 | 내용 | 결정 |
|---|---|---|
| A | global IP + 서버가 붙이는 짧은 번호(#1, #2) | 서버가 번호를 관리해야 해서 제외 |
| **B** | **global IP + 서버가 본 바깥 포트**로 방을 구분 | **선택.** 서버가 받은 연결의 출발 주소 자체가 고유하다. 기존 IP·포트 입력 칸을 그대로 쓴다 |
| C | 서버는 소개만 하고 두 PC가 직접 연결(NAT 홀펀칭) | 공유기·통신사에 따라 자주 실패해서 제외 |

방 이름 `IP:바깥포트`는 **서버 안에서만 쓰는 이름**이다. 공유기는 그 바깥 포트로 들어오는 데이터를 서버에서 온 것만 받으므로, 친구가 그 주소로 직접 접속하지 않는다. 모든 데이터는 서버를 거친다.

## 4. 동작

```
호스트 PC ──(나가는 TCP)──▶ 중계 서버 :47123 ◀──(나가는 TCP)── 클라이언트 PC
   HOST                       방 "211.36.10.5:53214"           JOIN 211.36.10.5 53214
   ◀── ROOM 211.36.10.5 53214                                   
   ◀── PAIRED                                                   ──▶ OK
   ═══════════ 이후 서버는 두 연결의 바이트를 그대로 양방향 전달 ═══════════
   (기존 HELLO → 로비 → START → INPUT/STATE → RESULT → 재대전, heartbeat 그대로)
```

### 4.1 중계 핸드셰이크 (게임 프로토콜 앞에 한 번만, UTF-8 한 줄 텍스트)

| 보내는 쪽 | 줄 | 의미 |
|---|---|---|
| 호스트 → 서버 | `HOST v1` | 방 만들기 |
| 서버 → 호스트 | `ROOM <ip> <port>` | 서버가 본 호스트의 출발 주소 = 방 이름 |
| 클라이언트 → 서버 | `JOIN v1 <ip> <port>` | 그 방에 들어가기 |
| 서버 → 클라이언트 | `OK` / `ERR NO_ROOM` / `ERR ROOM_FULL` / `ERR BAD_REQUEST` | 결과. ERR 뒤에는 서버가 연결을 닫는다 |
| 서버 → 호스트 | `PAIRED <clientIp>` | 친구가 들어옴. 이 줄 다음 바이트부터는 그대로 전달 |

- 한 줄은 최대 128바이트로 제한하고 `\n`으로 끝낸다. 형식 오류, 길이 초과, 핸드셰이크 5초 초과면 `ERR BAD_REQUEST` 후 닫는다.
- 버전 `v1`이 다르면 `ERR BAD_REQUEST`로 처리한다.
- 핸드셰이크 이후에는 기존 길이 접두 JSON 프레임이 그대로 흐른다. 서버는 내용을 해석하지 않는다.

### 4.2 서버 규칙

- 방 하나에는 클라이언트 하나만 들어간다. 이미 짝지어졌으면 `ERR ROOM_FULL`로 거절한다.
- 호스트가 10분 동안 짝이 없으면 방을 닫는다.
- 어느 쪽이든 연결이 끊기면 상대 쪽도 닫고 방을 지운다. 그러면 게임은 기존 끊김 처리(PEER_CLOSED/LOST → P2P 첫 화면)를 그대로 탄다.
- 동시 방 수는 256개로 제한한다. 넘으면 새 `HOST`에 `ERR BAD_REQUEST` 대신 `ERR FULL`로 응답하고 닫는다.
- 로그는 표준 출력으로 남긴다(방 생성·짝·종료, 주소·시각). 데이터 내용은 남기지 않는다.

### 4.3 게임 쪽

- **P2P 첫 화면에 "인터넷 대전(서버 경유)" 체크박스를 추가한다(기본 꺼짐).** 꺼져 있으면 지금 LAN 동작과 완전히 같다.
- **켜고 "호스트"를 누르면:** 서버에 `HOST`로 접속한다. 받은 `ROOM <ip> <port>`를 기존 "내 주소" 자리에 `211.36.10.5 / 포트 53214`처럼 보여 준다. `PAIRED`를 받으면 그 소켓으로 기존 연결 수립(HELLO 교환)을 이어 간다.
- **켜고 "접속"을 누르면:** 입력한 IP·포트로 `JOIN`을 보내고, `OK`를 받으면 기존 연결 수립을 이어 간다.
- **오류 안내(한국어):**
  - 서버 연결 실패: "중계 서버에 연결할 수 없습니다."
  - `NO_ROOM`: "그 주소에서 기다리는 방이 없습니다. IP와 포트를 확인하세요."
  - `ROOM_FULL`: "이미 대전 중인 방입니다."
  - 서버 응답 5초 초과: 기존 시간 초과 안내를 쓴다.
- **중계 서버 주소:** 기본값은 `158.179.174.70:47123`이다. 시스템 속성 `tetris.relay=host:port`로 바꿀 수 있다(테스트·다른 서버용).
- **바꾸지 않는 것:** 연결 이후 코드(`PeerConnection`, `SocketLobbyClient`의 로비·경기 처리, 프로토콜 메시지)는 수정하지 않는다. 수립된 `Socket`을 기존 경로에 넘기기만 한다.

## 5. 제약

- Java 21. 중계 서버는 같은 JAR 안의 별도 main 클래스(`tetris.relay.RelayServer`)로 둔다. 서버에서는 `java -cp SE-Tetris.jar tetris.relay.RelayServer 47123`로 실행한다.
- 서버 운영
  - 대상 VM은 E2.1.Micro(1/8 OCPU, 1GB)다. 연결마다 스레드 2개를 쓰고 메모리는 고정 버퍼(8KB)만 쓴다.
  - Oracle 보안 목록과 VM 방화벽에 TCP 47123이 이미 열려 있다.
  - VM에 Java 21(`java-21-openjdk-headless`)을 설치하고 systemd 서비스로 상시 실행한다.
- 기존 SSH 터널 실험은 이 서버가 47123을 쓰므로 함께 쓰지 않는다.
- 테스트는 loopback에서 로컬 `RelayServer`를 띄워 검증한다. 실제 Oracle 서버 접속은 수동 확인 항목이다.

## 6. 검증

- **자동**
  - 중계 핸드셰이크: 방 생성, 짝, 없는 방, 가득 찬 방, 형식 오류, 5초 초과, 한쪽 끊김 시 상대 닫힘, 10분 대기 만료(가짜 시계).
  - 같은 IP 다른 포트의 두 호스트를 정확히 구분.
  - 서버 경유로 두 `SocketLobbyClient`가 LOBBY → READY → START → 경기 → RESULT → 재대전까지 진행.
  - 체크박스 꺼짐 시 기존 LAN 테스트 전부 통과.
- **수동**
  - 실제 Oracle 서버에 배포한 뒤, 이 PC(집 Wi-Fi)와 상대 PC(휴대폰 핫스팟)로 대전한다.
  - `--dev` RTT를 기록한다.

## 7. 구현자에게 맡기는 것

- 체크박스·주소 표시의 정확한 배치(기존 P2P 패널 레이아웃을 따른다).
- 중계 서버 내부 자료구조, 스레드 이름, 로그 형식.
- 배포 스크립트 형태(`scripts/deploy-relay.ps1`, SSH 키 `~/.ssh/tetris_relay` 사용).

## 8. 내가 정한 것 (확인 필요)

- 핸드셰이크를 게임 JSON 프로토콜이 아닌 **별도 한 줄 텍스트**로 둔 것: 서버가 게임 프로토콜을 몰라도 되고, 기존 프로토콜을 바꾸지 않기 위해서다.
- 체크박스로 켜고 끄게 한 것(입력한 IP가 사설인지 보고 자동 판단하지 않음): 동작이 눈에 보이고, LAN 경로가 절대 바뀌지 않게 하려는 것이다.
- 방 대기 10분, 동시 방 256개, 핸드셰이크 5초.
