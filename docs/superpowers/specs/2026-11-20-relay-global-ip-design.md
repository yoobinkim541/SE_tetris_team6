# 다른 LAN 간 P2P 대전: 중계 서버 + 로비 코드 (Challenge) 설계

- 브랜치: `challenge/relay-global-ip` (origin/develop `d432f1c`에서 분기). **develop·main에 병합하지 않는다** (요구사항 3 p12).
- 상태: 설계 v2(Codex `gpt-6.1-sol` 리뷰 13건 반영), 사용자 승인 대기.
- 변경 이력: v1은 호스트의 `global IP:바깥 포트`로 방을 구분했다. 리뷰에서 바깥 포트가 재사용되면 예전 초대 주소로 다른 방에 붙는 문제가 지적되었다(RFC 9293 §3.4.1). 사용자 결정에 따라 **서버가 발급하는 로비 코드**로 바꿨다.

## 1. 의도

지금 P2P 대전은 같은 LAN에서만 된다. 서로 다른 집·학교·핫스팟에 있는 두 사람이 **공유기 설정(포트포워딩) 없이** 대전하게 한다. 접속 정보는 사람이 불러 주기 쉬운 **로비 코드 하나**로 한다.

요구사항 p8의 IP 표시·입력 흐름은 **기존 LAN 모드에 그대로 남는다.** 로비 코드는 challenge 전용 추가 모드다.

## 2. 목표 · 비목표 · 실패로 보는 것

- **목표**
  - 서로 다른 LAN의 두 PC가 Oracle 서버(`158.179.174.70`)를 거쳐 대전한다.
  - 호스트는 "인터넷 방 만들기"를 누르면 로비 코드(예: `K7QM2X`)를 받는다. 친구는 그 코드를 입력하면 들어온다.
  - 연결된 뒤의 로비·경기·재대전·heartbeat·지연·끊김 처리는 기존 코드(`PeerConnection`, `PeerLink`, `SocketLobbyClient`의 로비·경기 처리, 프로토콜)를 그대로 쓴다.
- **비목표:** NAT 홀펀칭, 채팅·다인 대전, 사용자 계정, 서버가 게임 엔진을 돌리는 방식, 여러 서버·로드밸런서, IPv6.
- **실패로 보는 것**
  - 기존 LAN 대전 동작이나 테스트가 바뀌는 경우.
  - 다른 사람의 방에 잘못 붙는 경우.
  - 서버가 꺼졌을 때 게임이 안내 없이 멈추는 경우.
  - 공개 포트 때문에 서버가 쉽게 마비되는 경우.

## 3. 방식

| 안 | 내용 | 결정 |
|---|---|---|
| v1 | global IP + 바깥 포트로 방 구분 | 바깥 포트가 재사용되면 다른 방에 붙을 수 있어 폐기 |
| IP + 포트 + 토큰 | 위에 무작위 토큰 추가 | 입력이 세 칸이라 제외 |
| **로비 코드** | 서버가 방마다 무작위 코드 발급, 코드로 입장 | **선택(사용자).** 한 칸 입력, 재사용 문제 없음, 사용자 IP를 화면에 노출하지 않음 |
| 홀펀칭 | 서버는 소개만, 두 PC가 직접 연결 | 공유기·통신사에 따라 실패해서 제외 |

계산은 지금처럼 호스트 PC가 한다(호스트 권위, Notion R3-D08). 서버는 두 연결을 짝지은 뒤 바이트를 그대로 넘기기만 한다.

```
Host ◀──▶ 중계 서버(158.179.174.70:47123) ◀──▶ Client
  두 PC 모두 서버로 먼저 연결(나가는 연결) → 양쪽 공유기 설정 불필요
```

## 4. 로비 코드

- **형식:** 6글자. 문자 집합은 헷갈리는 글자(0 O 1 I L)를 뺀 대문자·숫자 31종(`ABCDEFGHJKMNPQRSTUVWXYZ23456789`)이다. 조합 수는 31^6 ≈ 8.9억이다.
- **생성:** `SecureRandom`으로 만든다. 서버 실행 중에 한 번 쓴 코드는 다시 발급하지 않는다(발급 이력을 메모리에 보관, 최대 100,000개, 넘으면 오래된 것부터 버림).
- **입력:** 대소문자 구분 없음, 공백·`-` 무시. 화면 표시는 `K7Q-M2X`처럼 3+3으로 나눈다.
- **추측 방지:** 같은 출발 IP에서 `NO_ROOM` 응답이 1분에 10회를 넘으면 그 IP의 JOIN을 1분 거절한다(`ERR SLOW_DOWN`). 같은 학교·CGNAT 사용자도 정상 입장 몇 번은 충분하다.

## 5. 중계 핸드셰이크

게임 프로토콜 앞에서 한 번만 쓰는 UTF-8 한 줄 텍스트다. 서버는 이후 게임 데이터를 해석하지 않는다.

| 보내는 쪽 | 줄 | 의미 |
|---|---|---|
| 호스트 → 서버 | `HOST v1` | 방 만들기 |
| 서버 → 호스트 | `ROOM K7QM2X` | 발급된 코드 |
| 클라이언트 → 서버 | `JOIN v1 K7QM2X` | 입장 |
| 서버 → 클라이언트 | `OK` / `ERR NO_ROOM` / `ERR ROOM_FULL` / `ERR SLOW_DOWN` / `ERR BAD_REQUEST` / `ERR FULL` | 결과. ERR 뒤에는 연결을 닫는다 |
| 서버 → 호스트 | `PAIRED` | 친구가 들어옴. **클라이언트 IP는 보내지 않는다** |

- **바이트 경계:** 양쪽 구현은 `\n`까지 **바이트 단위로 정확히** 읽고, 그 뒤 바이트는 한 바이트도 버리지 않는다. `BufferedReader` 같은 미리 읽기 버퍼는 쓰지 않는다. 서버는 `OK`와 `PAIRED`를 **모두 쓰고 flush한 뒤에만** 양방향 전달을 시작한다. 그래서 제어 줄과 HELLO 프레임이 한 번에 붙어 와도 손실이 없다.
- **줄 제한:** 최대 64바이트이며, 읽는 도중 64바이트를 넘으면 즉시 `ERR BAD_REQUEST`로 끊는다.
- **버전:** `v1`이 아니면 `ERR BAD_REQUEST`로 끊는다.

## 6. 서버 규칙 (`tetris.relay.RelayServer`, 같은 JAR의 별도 main)

### 6.1 방 상태와 동시성

- 상태는 `WAITING → PAIRED → CLOSED`이고, 모든 전이는 방 객체 하나의 잠금 안에서 원자적으로 한다.
- 두 JOIN이 동시에 오면 하나만 `OK`를 받고 나머지는 `ERR ROOM_FULL`을 받는다.
- 만료·취소와 JOIN이 겹치면 이미 CLOSED인 방에는 `ERR NO_ROOM`을 준다.
- 맵에서 방을 지울 때는 코드뿐 아니라 **같은 방 객체인지**도 확인해서 지운다(`remove(code, room)`).
- 정리는 방마다 한 번만 한다. 양쪽 소켓과 pump를 닫고, 방을 맵에서 지우고, 통계를 갱신한다.

### 6.2 자원 제한 (E2.1.Micro: 1/8 OCPU, 1GB)

| 항목 | 값 |
|---|---|
| 동시 TCP 연결 | 최대 300 (accept 직후 검사, 넘으면 즉시 닫음) |
| 핸드셰이크 미완료 연결 | 최대 64 |
| 같은 출발 IP의 새 연결 | 1초에 5개 |
| 핸드셰이크 기한 | 접속 후 **절대 5초**(단조 시계 기준, 한 바이트씩 보내도 연장 안 됨) |
| 대기 방 | 최대 100개, 방마다 10분 후 만료(`ERR` 없이 닫음 → 호스트에 "방 만료" 안내) |
| 짝 맺은 방 | 최대 100개 |
| 무활동 | 짝 맺은 뒤 양쪽 모두 60초 동안 아무것도 안 보내면 닫음(정상 게임은 heartbeat가 0.5초마다 오므로 걸리지 않음) |
| 막힌 전송 | 한쪽에 쓰기가 10초 이상 끝나지 않으면 방을 닫음 |
| 방 전체 수명 | 최대 3시간 |

- 전달은 **방마다 방향별 pump 2개**로 하고, Java 21 **가상 스레드**를 쓴다. 버퍼는 pump마다 8KB다.
- 위 수치는 출발값이다. 배포 후 실제 대전 2판과 가짜 부하 100방으로 메모리(RSS)·FD·CPU를 측정해 조정한다.
- **반쯤 닫힘(half-close):** 한쪽이 FIN을 보내면 방 전체를 닫는다. 게임 프로토콜은 LEAVE 후 닫으므로 이 정책으로 충분하다.

### 6.3 운영

- 단일 VM, 단일 프로세스, 공인 IPv4 `158.179.174.70:47123`에 직접 접속한다(로드밸런서 없음). **IPv4 전용.**
- systemd 서비스로 상시 실행한다. Java 21(`java-21-openjdk-headless`)이 필요하다.
- 로그는 방 생성·짝·종료와 오류 코드만 남긴다. 출발 IP는 **추측 방지 판단에만 메모리로 쓰고 로그에는 남기지 않는다.** 로그는 journald 기본 보존(용량 제한 50MB)을 따른다.
- 전송은 **암호화하지 않는다**(challenge 시연 범위). 경로상 관찰·변조 위험을 문서에 명시한다. 게임 데이터에는 개인정보가 없다.
- 기존 SSH 터널 실험과는 포트가 겹치므로 함께 쓰지 않는다.

## 7. 게임 쪽 변경

### 7.1 연결 수립 진입점 (리뷰 blocker 1)

`PeerEstablisher`에 **이미 연결된 소켓으로 기존 HELLO 핸드셰이크를 시작하는 공개 진입점**을 추가한다.
- `Attempt adopt(Socket connected, PeerRole role, String displayPeer)`
- 동작: 기존 내부 `beginHandshake`와 같은 경로로 HELLO를 교환하고 `PeerLink`를 만든다. HELLO 5초 기한과 취소 처리도 기존 그대로다.
- `displayPeer`는 화면·통계에 보일 상대 이름이다. 중계 모드에서는 `"인터넷 · K7Q-M2X"`를 쓴다. `PeerLink.peerAddress()`는 이 값을 돌려준다.

새 클래스 `RelayConnector`가 서버 접속과 중계 핸드셰이크를 맡는다. 모든 I/O는 EDT 밖에서 하고, 결과는 dispatcher로 알린다.

| 단계 | 기한 | 실패 시 |
|---|---|---|
| 서버 TCP 접속 | 5초 | "중계 서버에 연결할 수 없습니다." |
| `HOST`→`ROOM` / `JOIN`→`OK` | 5초 | 서버 오류 코드별 안내 |
| 호스트의 `PAIRED` 대기 | 서버의 10분 만료까지(클라이언트 쪽 타이머 없음). 서버가 끊으면 즉시 실패 | "방이 만료되었습니다." 또는 "중계 서버와 연결이 끊겼습니다." |
| HELLO | 5초(기존) | 기존 안내 |

- **소켓 정리:** 각 단계가 끝나면 핸드셰이크용 `SO_TIMEOUT`을 0으로 되돌린 뒤 `adopt`에 넘긴다. 기존 `PeerConnection`이 읽기 시간 초과를 오류로 끊지 않게 하기 위해서다.
- **취소:** 취소·화면 종료·`leave`·`close`는 모든 단계의 소켓과 타이머를 닫는다. 기존 "시도 세대" 검사를 그대로 써서, 늦게 도착한 `ROOM`·`PAIRED`가 취소된 화면을 되살리지 않는다.

### 7.2 로비·화면

- **P2P 첫 화면:** "인터넷 방 만들기" 버튼과 "코드로 입장"(코드 입력 칸 + 버튼)을 추가한다. 기존 LAN의 포트·IP 칸과 버튼은 그대로 둔다.
- **코드 표시:** 호스트 대기 화면에 코드를 크게 `K7Q-M2X`로 보여 준다. 기존 LAN 주소 표시 대신 쓴다. `ROOM` 수신은 비동기로 화면을 갱신한다.
- **`SocketLobbyClient`:** `hostOnline()`, `joinOnline(String code)`를 추가한다. 반환은 기존 `host`/`connect`와 같은 `CompletionStage<Void>`이고, 수립 이후는 기존 경로를 그대로 탄다.
- **최근 접속 IP:** 인터넷 모드 연결은 **기록하지 않는다.** 코드는 일회용이고, 서버 IP를 상대 IP로 저장하면 안 되기 때문이다.
- **오류 안내(한국어):**
  - `NO_ROOM`: "그 코드의 방이 없습니다. 코드를 확인하세요."
  - `ROOM_FULL`: "이미 대전 중인 방입니다."
  - `SLOW_DOWN`: "잠시 후 다시 시도하세요."
  - `FULL`: "서버가 혼잡합니다. 잠시 후 다시 시도하세요."
  - 만료: "방이 만료되었습니다. 다시 만드세요."
- **기존 TIMEOUT 문구:** 기존 문구 "같은 LAN인지, 방화벽을 확인…"은 인터넷 모드에서는 "중계 서버 연결이 끊겼습니다…"로 바꿔 보여 준다.
- **서버 주소:** 기본값 `158.179.174.70:47123`, 시스템 속성 `tetris.relay=host:port`로 바꿀 수 있다(IPv4 숫자 주소만).

## 8. 검증

### 8.1 자동 (loopback, 로컬 `RelayServer`, 가짜 시계)

- **방·코드**
  - 방 생성·코드 형식
  - 코드 입장
  - 대소문자·하이픈 무시
  - 없는 코드
  - 가득 찬 방
  - 코드 재발급 금지
  - 10분 만료
- **경쟁 상황**
  - 동시 JOIN 2개 중 하나만 `OK`
  - JOIN과 만료·취소가 겹치는 경우
  - 만료된 방의 정리가 새 방을 지우지 않음
- **바이트 경계**
  - `OK`와 HELLO 프레임이 한 번에 붙어 와도 손실 없음
  - 한 바이트씩 나눠 와도 손실 없음
- **악용·자원**
  - 한 바이트씩 보내는 연결도 절대 5초에 끊김
  - 64바이트 초과 줄
  - 연결 수·미완료 수·연결 빈도 제한
  - `NO_ROOM` 추측 제한
  - 읽지 않는 상대로 막힌 전송 → 10초에 정리
  - 반복 접속 후 스레드·소켓이 남지 않음
- **장애**
  - 짝 맺기 전, HELLO 중, LOBBY, PLAYING 각각에서 서버나 상대의 FIN·RST·무응답 → 게임이 기존 끊김 안내로 P2P 첫 화면에 돌아감
- **통합**
  - 서버를 거쳐 두 `SocketLobbyClient`가 LOBBY → READY → START → 경기 → RESULT → 재대전 진행
  - 최근 IP 저장소에 아무것도 기록되지 않음
- **회귀**
  - 기존 LAN 테스트 전부 통과, `gradlew check`(LINE ≥ 70%)

### 8.2 수동

- Oracle 배포 후 이 PC(집 Wi-Fi)와 상대 PC(휴대폰 핫스팟)로 대전한다.
- `--dev` RTT를 판마다 200회 기록하고 p50·p95·최대를 남긴다. 합격 기준은 **p95 RTT ≤ 200ms이고 3판 연속 끊김 없음**이다. 입력→표시 200ms 판정은 별도 영상 측정이다.
- 서버에서 대전 2판 + 가짜 100방 부하로 RSS·FD·CPU를 측정한다.
