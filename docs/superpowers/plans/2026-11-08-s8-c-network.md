# S8 C 트랙: 호스트 대기·접속(S8-C1)과 로비 준비·시작(S8-C2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 두 PC가 LAN에서 호스트 대기→접속→HELLO 교환→로비(설정·양측 READY)→START 한 번까지 실제 TCP로 진행하게 한다.

**Architecture:** `PeerEstablisher`가 소켓 수립(listen/accept/connect)과 HELLO 핸드셰이크·타임아웃·취소를 맡고 성공 시 `PeerLink`(연결 + 역할)를 돌려준다. `SocketLobbyClient`가 develop의 `LobbyClient` 계약을 구현해 `PeerLink` 위에서 CONFIG/READY/START를 주고받는다. 모든 상태 변경과 콜백은 주입한 dispatcher(앱은 EDT) 한 스레드에서만 일어난다.

**Tech Stack:** Java 21(`options.release = 21`), Swing EDT, JUnit 5, Jackson(이미 의존성), Gradle Wrapper(`gradlew.bat`).

## Review Focus

1. 취소 직후 늦게 끝난 이전 시도(worker/타이머)가 새 시도의 연결을 닫거나 결과를 덮어쓰는 경우 → 새 연결 유지.
2. HELLO가 오기 전에 상대가 바로 끊거나 같은 역할(HOST↔HOST)로 HELLO를 보내는 경우 → 실패로 끝나고 소켓 닫힘.
3. 호스트가 설정을 바꾼 직후 상대의 이전 revision READY가 도착하는 경우 → 무시, 시작 안 함.
4. 양쪽 READY가 거의 동시에 오거나 START가 두 번 오는 경우 → START는 한 번, matchId 하나.
5. 로비 중 상대 프로세스 종료·`leave()`·`close()` 중복 호출 → INITIAL, 예외 없음, 스레드·포트 해제.

**동작 결정:**
- `host(port)`: 호출 스레드에서 `new ServerSocket()` + `setReuseAddress(false)` + bind(`0.0.0.0`, port). `BindException`→ `PORT_IN_USE`로 **즉시** 실패한 future. 이후 daemon 스레드가 `accept()` 1회 후 서버 소켓을 닫는다(두 번째 접속 차단). accept 대기에는 타임아웃 없음(취소 전까지 대기). 
- `connect(address, port)`: `PeerAddress.parse` 실패 시 즉시 `INVALID_ADDRESS`(스레드 시작 안 함). daemon 스레드에서 `socket.connect(addr, timeoutMillis)`; `ConnectException`→`REFUSED`, `SocketTimeoutException`→`TIMEOUT`, 그 외 `IOException`→`IO_ERROR`.
- 소켓이 연결되면 `PeerConnection.start(socket, dispatcher, handshakeListener)` 후 자기 역할 HELLO 전송. 이 시점부터 `timeout` 타이머 시작(공유 daemon `ScheduledExecutorService`). 상대 HELLO가 반대 역할이면 성공, 같은 역할이거나 HELLO 전에 다른 메시지/종료면 `PROTOCOL_ERROR`(종료면 `IO_ERROR`).
- 결과 확정(성공·실패·취소)은 시도마다 `AtomicBoolean settled`로 한 번만. 확정은 dispatcher에서 `future.complete/completeExceptionally(new EstablishException(...))`. `cancel()`은 dispatcher에서 불리며 `future.cancel(false)` 후 서버 소켓·소켓·연결을 닫는다. 확정 뒤 도착한 늦은 결과(accept 성공, 타이머)는 자기 자원만 닫고 아무것도 하지 않는다.
- `PeerLink`: 핸드셰이크 뒤부터 `attach` 전까지 받은 메시지와 종료 통지를 버퍼에 쌓고, `attach`(dispatcher에서 호출) 때 순서대로 넘긴 뒤 바로 전달 모드로 바꾼다.

  - `호스트와_클라이언트가_HELLO를_교환하고_역할과_주소를_얻는다`: `host(0)` + `connect("127.0.0.1", localPort)` → 역할 HOST/CLIENT, `peerAddress()=="127.0.0.1"`

**Interfaces:**

**동작 결정 (모든 메서드·콜백은 dispatcher 스레드):**
- 초기 스냅샷 `new LobbySnapshot(Role.NONE, State.INITIAL, null, 0, false, false, null)`.
- `host(port)`/`connect(address, port)`: INITIAL에서만(아니면 `IllegalStateException`). HOSTING/CONNECTING 발행. 성공 시 `link.attach(this)`, LOBBY 발행(`peerIdentity = link.peerAddress() + "#" + 연결 번호`), 반환 stage 완료. 실패 시 INITIAL 발행 후 stage 예외 완료(원인 `EstablishException`).
- `cancel()`: 진행 중 시도 취소, stage 취소, INITIAL. `leave()`: 연결 닫고 INITIAL. 둘 다 반복 호출 무해.
- `selectConfig(c)`: `snapshot.selectConfig(c)`로 검증(클라이언트면 `IllegalStateException`), revision이 `Integer.MAX_VALUE` 초과면 `IllegalStateException`. 발행 후 `MatchPayloads.configMessage(c, (int) revision)` 전송.
- `ready(rev, value)`: `snapshot.readyAtRevision(rev, value)`로 검증 후 발행, `LobbyPayloads.readyMessage` 전송. 호스트면 양쪽 ready 확인(아래).
- 수신 CONFIG: 클라이언트만 적용(새 config·revision, 양쪽 ready false). **호스트가 받은 CONFIG는 무시**(설정 불변).
- 수신 READY: 봉투 revision == 현재 revision이고 state LOBBY일 때만 `peerReady` 갱신, 아니면 무시.
- 호스트 시작 판정: LOBBY에서 `localReady && peerReady` → `matchId = UUID` 생성, `startMessage(matchId, rev)` 한 번 전송, STARTING 발행. STARTING 이후 CONFIG/READY 수신은 무시, `selectConfig`/`ready` 호출은 `IllegalStateException`.
- 수신 START(클라이언트): LOBBY이고 revision이 현재와 같고 `localReady && peerReady`일 때만 STARTING + matchId 저장. 그 외(이전 revision, 이미 STARTING) 무시.
- `onClosed`(상대 종료·오류): INITIAL 발행, matchId 초기화.
- `battleClient()`: 항상 `Optional.empty()`(경기 핸드오프는 S9-C1). `close()`: 반복 무해, 시도 취소·연결 닫기·구독 해제; 이후 명령·구독은 `IllegalStateException`.
- `subscribe`: 현재 스냅샷 즉시 1회, 이후 순서대로. 해제 후 콜백 없음.
